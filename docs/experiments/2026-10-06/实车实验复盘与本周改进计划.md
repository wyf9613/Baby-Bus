# 2026-10-06 实车实验复盘与本周改进计划

日期：2026 年 10 月 6 日。对象：Baby-Bus main 的单文件 MVP policy，基线 `e0d226e`。当天测试过旧车和新车；新车地址为 `10.43.254.27`。本周剩余时间没有实车实验机会，因此以下改进计划以日志回放、离线模型和软件验证为主。

## 1. 本次实验结论

我们从“服务启动、策略运行，但车不动”，推进到了新车能够连续前进并自动停止。转向符号修正及油门补偿后，用户确认“都正常了”；最好的一轮记录了 **2.015 米轮速积分距离、10.54 秒运行时间、0.333 m/s 最高轮速**，现场确认正常前进并停止。**尚未完成 3 米实车验收。**

当天的问题涉及服务监督器开销、配置与源码不一致、传感器时序、车辆动力响应、转向符号，以及规划有效性判定。把所有问题统一解释成“车坏了”或“policy 太慢”都会遗漏关键原因。

对本周改进的两个判断：

1. **性能需要成为设计约束。** 日志明确显示 DREAM runtime runner 的进程扫描和运行记录校验有高开销；策略节点在传感器运行时也有明显 CPU 占用。我们需要按进程、阶段和最坏延迟定位，而不能只看 `python3` 名称或平均频率。
2. **当前策略对输入波动过于敏感。** 一次道路拟合失败、覆盖略不足、曲率越界或参考过期，就可能进入持续零输出、必须显式重启的状态。这保留了停止行为，却缺少短暂波动下的降级运行能力。重点应是明确哪些情况可以恢复、恢复期间如何约束运动，而非把全部门限继续放宽。

### 证据范围

- 文中的“距离”均为轮速积分；没有卷尺或独立定位系统验证车身位移，滑移、编码器比例及停车后滑行会影响结果。
- “现场确认”来自用户观察；存在遥测显示轮子运动但现场没有看到车身前进的试验，不能把该轮当成已确认实车成功。
- Disabled 下的策略试算可以验证计算与状态流程，不能验证动力、转向或物理停车。
- 软件测试通过可以验证规定场景中的行为，不等于已验证真实感知质量、时延或赛道表现。
- 目录内部分 `mvp-run-result`、`confirmed-result`、`main-3m-result` 是别名或最新结果副本；不能累加成独立实验次数。[结果索引](实验结果索引.csv)保留了全部 29 个含结果字段的文件条目，并标出主要副本。

## 2. 环境、启动和部署排查

### 2.1 服务与车辆使能

最初只有 `/car/ai4r_policy` 节点。ROS 话题列表里出现传感器话题，并不证明存在正常发布的传感器节点：策略的订阅也会让话题出现在列表中。随后逐项启动相机、车辆接口、IMU 和 Foxglove，才收到实际传感器数据。

老师文档规定两步操作：先请求车辆 Enabled，再请求策略 state 3。启动软件服务不会自动使车辆运动；策略重启后回到零输出。本次已分别验证车辆状态和策略状态，避免把“策略正在发布 actions”当成“车辆已接收并执行油门”。停止时先请求策略 state 2，再请求车辆 Disable。

旧车车辆接口多次报告 `worker receive-service gap`、`negotiation timeout/deadline`，连接次数和 session 变化。停止相机/雷达后，一段 10 秒观察内车辆连接稳定；重新启动相机后又出现断连。这支持“共存负载或通信条件影响连接”的判断，**不能单凭这组对照确定 CPU 是唯一原因**。内核日志中还存在相机 USB 重新枚举，需要与正常启动、停止时间对应分析。

### 2.2 源码被覆盖与配置不一致

main 分支切换成功、student workspace 构建成功后，车端 `scripts/policy_node.py` 和 YAML 又出现大规模本地变化。简化版脚本缺少 `ControlSettings`，运行模式变成 `cone_detection`，`control.enabled`、`control.mode` 未声明。后来出现“YAML 已恢复、脚本仍被覆盖”的组合：参数显示 timer，却仍查不到 control 参数。

备份、stash、恢复 main、构建和重启后，才确认运行的是完整 MVP。刚重启时查询得到一次 `Node not found`，也应区分进程启动/发现延迟与源码错误。覆盖由谁或哪个流程造成，现有证据没有确认。

**改进要求：每次部署留下实际脚本哈希、有效参数、启动命令和版本。** 仅记录 Git HEAD 不够；symlink 安装会直接加载工作目录中后来被改写的源文件。

## 3. 性能与时序实验

### 3.1 CPU 归属和 profiler 结果

现场曾记录：仅启动 policy 服务时，`runtime_runner` 约占 85% CPU，真正的 `policy_node.py` 约占 4.3%。传感器共同运行时，策略进程约占 32%；多个 runner 各自占用较高。Linux 进程 CPU 的约 100% 通常对应一个逻辑核，不能把它直接理解成整台机器占用 100%。

完整 runner profile 显示两个明显的开销来源：

| 来源 | 记录中的证据 | 结论 |
| --- | --- | --- |
| 进程组扫描 | 原实现枚举所有 PID，并逐个读取 stat/status/stat；profile 中 41 次 `group_members` 累计约 7.17 s | 存在重复扫描和读取开销 |
| 运行记录校验和参数序列化 | 优化后 profile 中 `_open_run` 仍频繁执行，`parameter_file_bytes`/YAML `safe_dump` 1138 次，累计约 7.61 s | 扫描优化后仍存在另一处热点 |

这些是 profiler 的累计耗时，含嵌套调用，不能相加成总耗时；两次 profile 的监督循环次数也不同，不能用其总时间作为严格 CPU A/B。

已做的 runner 修改：先用内核进程组 ID 筛选候选，再为候选执行完整身份、UID/session 和进程组存在验证。单次扫描基准 **75.96 ms → 1.70 ms，约 44.6 倍加速**。runner 定向检查 53 项、旧车 DREAM 完整 fast gate 1264 项通过。完整身份校验和停止前检查仍保留。

**扫描快了不代表整体 CPU 问题已解决。** 新车应用相同修改后，runner 仍有较高 CPU 占用，后续还出现过车辆重连。

根据 `final-services-cpu.json` 逐进程重新统计：

| 进程 | 短采样平均 CPU |
| --- | ---: |
| policy 对应 runner | 73.46% |
| IMU 对应 runner | 68.38% |
| vehicle 对应 runner | 74.32% |
| camera 对应 runner | 72.48% |
| 实际 policy 节点 | 32.24% |
| 实际 vehicle interface 节点 | 11.25% |

四个 runner 的平均值为 **72.16%**。此前阶段报告中的“每个约 36.1%”与这份原始数据不一致；本综合文档以重新统计值为准。该短采样仍不能代表全天稳态负载或严格优化前后对照。

证据：[扫描基准](evidence/runner-fix-20261006/scan-benchmark.json)、[修改前 profile](evidence/runner-fix-20261006/before-runner.txt)、[修改后 profile](evidence/runner-fix-20261006/after-runner.txt)、[CPU 原始采样](evidence/runner-fix-20261006/final-services-cpu.json)。

### 3.2 policy 计算耗时与调度间隔

已有 wrapper 记录 `calculate_policy_actions` 的调用耗时和间隔；本次整理对 266 条记录重新统计：

| 指标 | 中位数 | P95 | P99 | 最大值 |
| --- | ---: | ---: | ---: | ---: |
| 策略计算耗时 | 3.50 ms | 5.17 ms | 6.31 ms | 7.57 ms |
| 相邻策略计算间隔 | 49.96 ms | 51.73 ms | 53.24 ms | 54.46 ms |
| 参考剩余有效时间 | 128.20 ms | 137.77 ms | 139.02 ms | 142.17 ms |

这段记录是在特定诊断条件下取得，不能代表所有共存负载。另一次现场 `ros2 topic hz` 虽显示平均约 20 Hz，最大消息间隔却达 **331 ms**。二者不是同一采样窗口；前者计算很快，后者仍可能出现调度、执行器阻塞或传输/观察延迟。

当前 profiler 没覆盖整个 policy 进程、全部传感器回调和执行器等待，因此 **不能从计算耗时小就断言 policy 完全没有性能问题**。已确认的可优化候选包括：相同锥桶帧在多次 timer 更新中重新拟合、观察数据深拷贝、高频 IMU 中可选字段处理和 TF 查询；各项实际占比尚未量化。

证据：[计算时序日志](evidence/timing-fix-20261006/policy-timing.jsonl)、[本次统计摘要](统计摘要.json)。

### 3.3 延迟与参考过期

相机 acquisition-to-publish 延迟常见约 0.19–0.22 s。初始 `planning.max_source_age_s=0.2` 几乎与处理延迟相同，数据到达时已接近或超过门限，出现 `stale_road`。参考寿命初始只有 0.1 s，叠加调度波动后，多次出现 `Control reference expired`。

当天逐步调整了相机源时效、参考寿命和运动历史覆盖区间，最终车端分别为 0.4 s、0.2 s、0.4 s。参考还受所依赖传感器的剩余期限限制，不能把 0.2 s 理解成所有路径都无条件可用 0.2 s。调整后的旧车 Disabled 策略试算曾持续 12 秒通过，但不能据此认为所有实时问题已经解决。

IMU 的分字段消息中，协方差首项 `-1` 表示该字段缺失。全零四元数伴随这个标志时，不能当成有效姿态；也不能因此把同消息中有效的加速度或角速度一并拒绝。多次 `imu_specific_force` 乱序警告不等于每次都缺少必需角速度。最终也发生过一次必需角速度 stale 导致启动拒绝，需要保留该区别。

### 4.4 转向符号与油门断续

原地不加油门的转向检查，请求 normalized steer `+0.4`。用户从车尾看向车头确认前轮朝右。控制器的正方向假设与这台车相反，因此车端设置 `control.mvp_steering_direction=-1.0`。修改后用户报告方向改善。

油门断续有独立原因：速度上升后 PI 输出下降，实际驱动落入电调低响应区间；用户反馈走一下停一下。当天加入可配置的持续油门补偿，车端设 0.30，并把速度增益从 `kp=1.4, ki=0.6` 调到 `kp=0.35, ki=0.08`。后续 B11、B12 用户确认正常，支持这组调整改善了当时的行驶表现。

通用代码默认补偿仍为零；停止、无效反馈和参考过期时输出零。恒定补偿是临时实车调参成果，后续需要验证不同电池状态、低速目标及饱和时的行为，不能用它代替完整动力辨识。

### 4.5 停车和静止输出检查

## 5. 为什么边界条件影响正常运行

### 5.1 当前停机处理的实际含义

`PolicyStopRequest` 被框架捕获后转为 state 2，节点继续工作并持续发零指令；大多数上述记录属于主动停止请求，**不是 Python 进程崩溃**。真正未预期的异常另走 traceback/error 路径。

问题在于两类情况的处理结果过于接近：输入出现可恢复的波动，也可能和严重故障一样立即锁定停车、清空运动历史和控制器状态，必须重新请求 state 3。这会让一次失败帧中断整轮运行；重新开始又需要积累延迟相机所需的运动历史。

把 `raise` 改成 `return` 本身不解决鲁棒性。需要改变“失败原因→运行行为”的规则，并说明缓存路径能用多久、如何移动到当前坐标、什么时候必须停。

### 5.2 当天门限冲突

| 条件 | 当天现象 | 本周应解决的问题 |
| --- | --- | --- |
| 相机源年龄 0.2 s | 处理延迟已约 0.2 s，stale_road | 按延迟分布分配时效预算，保留原采集时间 |
| 参考寿命 0.1 s | 平均 20 Hz 仍可能过期；现场有 331 ms 间隔 | 区分参考更新晚、数据真过期与调度问题 |
| 近端覆盖 ≤0.5/0.7 m | 道路仍可见，但有效拟合区间起点略远就拒绝 | 把可见距离与速度、预瞄位置关联 |
| 远端覆盖 ≥1.5 m | 3 m 短赛道后半程难以一直满足固定预瞄 | 让预瞄适应剩余可见范围，明确终点处理 |
| 双侧边界必须同时有效、未知宽度拒绝单边 | B08、B12 单侧拟合失败即停止；原始检测可能仍有两种颜色 | 输出每侧失败原因，区别点数不足、离群点和几何异常 |
| 小曲率范围 | 实际拟合出现约 0.18 1/m，0.15 门限触发 | 处理拟合波动，区分真实弯道与估计噪声 |
| 硬置信度筛选 | 回放变好，0.85 实车却仅跑 0.425 m | 在过滤噪声和保留覆盖之间联合评估 |
| 起步历史要求 | profiling 中 16 条 missing_motion_history、1 条 motion_interval_too_long | 完成有界起步预热，再开始有效控制 |

其中 B12 停车时记录道路 `right_only`、速度和角速度仍有效，说明当时触发原因来自道路估计。这支持用户对鲁棒性的反馈，但不能据此认定该条输入一定可以安全继续使用。

### 5.3 离线回放为何没有直接带来更长实车距离

对 B12 周围及停车后记录的 437 帧回放，置信度 0.75/0.80/0.85 分别得到 117/119/177 个有效道路估计。0.85 的部分失败帧恢复，但仍有曲率超限帧，并且下一轮实车出现了新的覆盖不足问题。最终恢复 0.75。

437 帧包含起步、行驶和停车后观察，不能拿其中的有效比例当作整段闭环成功率。固定日志不能反映控制变化后车辆的新轨迹；离线评价还应考察连续失败最长时间、覆盖变化、路径跳变和闭环偏移，而不只数“valid=True”。

### 5.4 固定 3 米距离与 3 米锥桶赛道

“跑满 3 米”与“前方一直保留 1–1.5 米有效双边道路”在仅 3 米的锥桶布局上可能冲突。车辆接近终点时，剩余可见赛道天然缩短；调大距离上限不会增加相机能看到的道路。

B12 的直接原因是拟合失败，不能断言一定由终点造成。要在短赛道完成任务，应离线设计自适应预瞄和终点模式，再下次实车验证。终点模式必须依赖明确的路线/终点定义和可信里程预算；短时几何预测也不能无限延长失去观测后的行驶。

## 7. 本周离线改进计划

以下是待实施、待验证的工作；不能把今天的通过记录当成这些新方案的验收。本周优先交付可回放、可测量的候选，下次现场做动力和短赛道验收。

### P0：冻结现场基线，先把问题变得可复现

**交付：** 保留本次 2 米参数为基线，建立统一日志格式和部署清单。每次启动记录代码哈希、有效参数、触发模式、必需传感器和车辆接口版本；每个 run 有唯一 ID，结果文件不再静默覆盖。

日志必须补充：每侧原始/筛选/内点数量、拟合系数与残差、实际曲率、有效 x 范围、当前值与门限、观测年龄、参考 deadline、控制状态及 requested/applied。今天只记了 `unsupported_road_curvature` 而缺少故障那一刻曲率值，增加了排查成本。

**完成判据：** 根据归档日志可复现 B11 的曲率拒绝、B12 的单边拟合失败和 B14 的覆盖不足；缺少字段时明确标为“无法重建”，不填入猜测数据。避免再发生“Git HEAD 正确但运行文件已被覆盖”的不可追溯部署。

### P1：性能测量与减少重复工作

**policy 侧：** 增加可开关的轻量阶段计时，覆盖传感器回调、TF、快照、道路拟合、运动对齐、规划、控制和发布。输出调用数、P50/P95/P99、最大耗时和 deadline miss；聚合后低频打印，限制日志容量。详细 profiler 只在短诊断窗口开启。

**优化候选：** 同一锥桶帧只做一次原始边界拟合，20 Hz 更新复用该结果并按新运动历史对齐；只缓存原始拟合，不能把已经对齐的路径重复变换。减少不必要的深拷贝和可选传感器处理。TF 缓存只有在安装变换确实固定时使用，并处理重启/变换变化；动态 TF 不可当成静态事实缓存。

**runner 侧：** 继续测量运行记录打开、不可变元数据校验和 YAML 序列化；在保持防篡改/身份验证语义的前提下考虑受控缓存与快慢路径。停止请求和实际发送信号前的身份检查仍要及时执行，不能把整个监督周期随意改慢。

**完成判据：** 在固定回放负载、相同记录长度和进程组合下比较优化前后调用数、分阶段耗时和整体 CPU。相同数据不能反复拟合；日志关闭后仍能运行。候选目标是策略计算 P99 ≤10 ms、正常 20 Hz 更新不因自身计算错过周期；这只是软件开发目标，Mac/x86 的测量不能宣称满足 Jetson 的实时预算，下次现场必须复测。

### P1：把输入质量问题分级，增加有界降级

建议保留外部 FSM 1/2/3 接口，先在运行状态内部区分以下行为：

| 类型 | 例子 | 拟议行为 |
| --- | --- | --- |
| 正常运行 TRACKING | 新鲜、可用的双边道路和运动反馈 | 正常计算控制 |
| 短暂质量下降 DEGRADED | 一帧拟合失败、短暂单边、置信度下降 | 仅在最近可信路径尚有效、运动历史可用时短时预测、减速；记录退化原因 |
| 持续感知失效 | 连续失败超出时间预算、预测路径到期 | 持续零输出，退出运行并要求显式重启 |
| 必须停止的故障 | 非有限输出、时钟异常、运动反馈超过期限、严重几何越界、车辆/操作者停止、距离或时间预算达到 | 停车；保留锁定和显式恢复 |

短时预测的起始研究范围可设为 0.15–0.25 s，最终预算要由源数据剩余期限、运动误差和速度共同约束。它是待测试方案，不是已经测得的安全持续时间。旧路径的原采集时间必须保留；新数据到来前不能把旧参考重新标成“新鲜”。

软条件应同时考虑持续时间和滞回，而不是单纯数 timer 次数。重复使用同一个失败相机帧也不能当成多帧独立失败。严重越界直接停车，不经过软条件延迟。

预期的质量下降返回明确的状态/原因码；未预期的程序错误保留异常和 traceback。性能和鲁棒性的关键是失败处理策略，不是异常语法本身。

**完成判据：** 一帧可恢复的噪声不会无条件终止整轮；连续丢帧、过期运动反馈和非法输出仍能在规定期限内转为零。硬停止后新数据不能自行启动。每种降级都有独立上限，速度/距离预算不中断、不重置。

### P2：改进边界拟合和短赛道参考

用今天原始锥桶批次比较加权鲁棒拟合、离群点处理和时间连续性约束。联合看点数、残差、宽度及覆盖，避免把检测置信度当成唯一质量标准。适当使用先前可信双边估计形成的有龄期宽度，而非临时猜一个宽度；失效、重启、时钟异常后应清除。

预瞄距离随速度和实际可见范围调整；如果只够短距离参考，应先减速而非要求永远覆盖 1.5 m。规划参考和控制器的有效范围要一起修改，不能生成控制器无法求值的路径。

对“赛道仅 3 m、终点后没有锥桶”建立离线终点场景。先定义终点如何获得，以及剩余距离/停车位置的不确定性，再考虑终点模式。若以 wheel integral 为终点依据，必须把比例误差、滑移及停车后位移纳入下次验收，不能承诺刚好在物理 3 m 点停住。

**完成判据：** 回放报告连续无参考最长时间、路径跳变、曲率/宽度变化和拒绝原因；闭环模型评估跟踪误差与完成率。提高 valid 帧数不能作为唯一通过条件。端点模式不能无限预测未观测道路。

### P2：完善低速油门控制与车辆配置

把转向符号、起步努力和持续驱动补偿作为带车辆身份的实验配置保存。离线比较现有 PI+补偿与起步/跟踪两阶段控制，检查饱和、积分和目标变零后的输出。加入速度低于目标且长期无运动的诊断，区分动力未响应和感知主动停止。

本周可以完成不同死区、启动迟滞和动力增益的模型敏感性分析；实际死区、不同电池条件及 steering trim 仍需下次现场测量。拟议零目标和停止路径必须完全绕过油门补偿。
