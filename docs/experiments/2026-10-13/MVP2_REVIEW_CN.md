# MVP2.0 实车实验复盘：2026-10-13

日期与时区：2026-10-13，Australia/Melbourne。车辆：`10.43.254.20`。
基线：`mvp2.0@ae74be454bccec472c677092afb35de899cdc130`。
目标：使用锥桶道路完成一次最多 3 m 的自主运行，保留 lattice 规划与候选上限 16。
现场此前确认场地清空、有人持遥控器看护。复盘时人员已回家、车辆不可连接；
本报告只使用当天已下载的证据，不追加车辆测试。

## 结果与判断

**今天没有完成自主 3 m，也没有取得自主车辆运动成功的证据。**
有两轮通过启动确认并产生约 0.303 的归一化驱动请求，轮速和累计里程始终为 0；
其中 100 ms 预算那轮，现场明确确认车轮和车身都没动。另一次没有同步人工观察。
其余已归档尝试因配置、连接、道路几何、时效或启动确认而未产生非零驱动。

失败不是一个统一的“lattice 规划不出来”。今天分别出现了：

1. 输入场景不满足颜色顺序，或双侧近端共同覆盖不足，尚未进入搜索即被拒绝。
2. 起步近端边界需要延拓，近似车身与延拓边界的净空检查失败。
3. 单帧无解原本直接锁停；新增静止重试后，时效失败又频繁打断三帧启动确认。
4. 有效规划与控制确实运行过，但给出的起步油门较小、车辆没有响应。
5. 规划耗时、输入剩余寿命、异步交付与控制取用没有形成稳定的端到端时间预算。

已证实的直接阻塞和未验证的物理原因在下文分开记录。最终的 0.2 m/s 起步修复
已部署，但两次尝试都没有执行到控制器，不能称为已解决或已证明无效。

## 失败原因复盘

### 近端几何问题不能只看道路总宽度

加宽并不一定有效：双侧共同观测起点、局部曲率、车辆相对位置，以及后向延拓后的
车旁边界都会影响结果。独立隔离采样定位到一帧起始姿态右后角 `(-0.198,-0.125) m`：
原始法向净空 0.03824 m，扣除硬余量 0.02000、延拓 0.06216、插值 0.00103、
扫掠 0.02500 m 后为约 -0.06995 m。即使把硬余量单独设为 0，仍为约 -0.04995 m。

该边界来自未直接观测的近端延拓，不能据此证明真实车身碰撞；也不能把后续采样
当成之前运动尝试的同一帧。它证明了“只减硬余量”不能解决该采样帧的问题。
输入与数值见 [边界分析](evidence/reports/road-v2/boundary-analysis.json)。

### 全 lattice 暴露了开关耦合、有限采样和首次参考问题

初次关闭 recovery 错误地同时切换到更严格的起步域；独立 dispatch 开关已解决
这一耦合。之后的无解还不能仅归因于“直线延伸 2 m 撞边界”：曲线候选、共同支持、
车身边界和运动约束都参与检查，早期日志恰好缺失候选明细，不能补猜原因。

保留的采样是长度 0.6/1.5 m、目标中心偏移 0 加当前 d0、时长 3 s、末速 0.1/0.2
m/s 与停车；16 只是 cap。由于共用道路与起始姿态，若起始车身检查就失败，增加
候选也未必有效。有限静止重试改善了“单次失败立刻停车”，却未解决输入时效；
3 帧确认在失败时清零，形成“可行一次—过期—重来”的持续启动阻塞。

### 时效预算不一致是最后两轮的直接阻塞

感知相机年龄预算 1.5 s，不等于规划能用 1.5 s 旧道路。规划道路上限仍为 0.4 s，
轮速和 IMU 各 0.25 s，参考寿命上限 0.2 s。相机约 0.2 s 的生产延迟、估计与
调度时间已消耗预算，lattice 的 100 ms 计算额度也不会延长参考绝对到期时刻。

最后两轮的 33 条拒绝记录中，6 条为初始运动历史不足，27 条为源期限错误；
其中 **23 条已成功选路、在主进程取用时以 reference_expired 丢弃，4 条在 worker
内就耗尽输入寿命**。该统计仅覆盖打印出的拒绝记录，不是全部任务的总体失败率。

| 示例 | 输入允许剩余时间 | 规划耗时 | 结果 |
| --- | ---: | ---: | --- |
| 第一轮 #4，道路年龄 309.999 ms | 90.001 ms | 44.563 ms | 已选中目标 0.2，但主进程取用时过期 |
| 第二轮 #5，道路年龄 259.264 ms | 140.736 ms | 45.354 ms | 已选中目标 0.2，但主进程取用时过期 |
| 第一轮 #10，IMU 年龄 233.780 ms | 16.220 ms | 50.153 ms | worker 内输入寿命耗尽 |
| 第二轮 #16，道路年龄 357.479 ms | 42.521 ms | 63.465 ms | worker 内输入寿命耗尽 |

`source_deadline_during_planning` 同时用于 worker 内期限失败和 transport 时过期，
名字容易误导。原始 `timestamp_s` 是输入状态参考时刻，不是 worker 完成时刻。
原始 `valid_for_s` 没有直接打印，可按记录年龄及代码公式还原；准确的进程接收/
控制 poll 时刻未记录。记录器收到错误日志的墙钟时间不能冒充结果接收时刻，
因此暂时无法把 IPC、任务排队、主线程调度、控制刷新各自耗时定量拆开。

完整字段与来源标记见 [时序报告](evidence/reports/startup-speed/TIMING_REPORT.md)、
[逐条 JSON](evidence/reports/startup-speed/TIMING_DETAILS.json) 和
[CSV](evidence/reports/startup-speed/TIMING_DETAILS.csv)。

### 起步速度与驱动力衔接问题已经定位到代码，但物理效果未验收

上周 main 归档的成功实车部署参数是前馈 0.30、驱动上限 0.35、速度 PI 0.35/0.08，
与今天一致。不能拿 main 根 YAML 的默认参数当成当时实车部署值。
上周 V1 直接给控制器 0.2 m/s，静止时比例项加前馈触及 0.35；今天 lattice 用
3 s 加速曲线的 0.3 s 预瞄，静止重复规划时目标只有约 0.0028–0.0056 m/s，
驱动请求接近前馈，实际约 0.302–0.303。测得零速后重新起算，难以自行提高目标。

本轮按用户要求将正常非停车 MVP 目标设为建议巡航速度下限。日志已出现
`preview≈0.0056, floor=0.2, command=0.2, measured=0`，证明 worker 中修复生效；
这些结果随后过期或没完成首次确认，尚无修复后的非零驱动或实际起步证据。

车端请求约 0.303、应用值 0.272 和 PWM 1568 μs 的差值，可由固件源码中 0.04
主机死区重映射解释，不能直接认定指令丢失。Enabled、host_permitted、应答序号
推进说明当时主机命令链路有响应。遥控器后来能走是现场确认；不能因此断言电池/
电调故障，也不能认定 0.303 必然低于起动门槛。起动门槛尚未测量，上周归档车辆
IP 是 `.27`、今天是 `.20`，不能直接假定两车物理标定一致。

下限目标是 MVP 的空间路径跟踪目标，仍不同于导出的纵向时间剖面；未来如果要
宣称严格跟踪 s(t)，还需统一规划速度剖面和控制速度查询。

### 版本漂移与监测脚本影响了实验可比性

今天数次发现其他会话修改车端代码或 YAML，包括控制关闭、目标改 0.1，以及
最后部署前 YAML 被替换成另一套 cone follower 配置。已备份后按授权恢复指定
候选，并加入启动前/运行中的哈希检查；没有把未知修改直接当作本版本测试。
一次旧状态误判是测试监测器问题，已修正为等待当前状态消息。

应继续保持“一个明确部署版本、一个写入者、每轮参数与哈希”的记录习惯。
policy state 2 + 底盘 Disabled 表示主机持续零输出，不一定等于遥控器接管；
本次没有借复盘再切换车辆模式，最后已确认状态只代表当时收尾，不声称离线后的
当前实时状态。

后续建议顺序（本次只记录，未实施）：

1. 先补齐原始参考寿命和端到端分段时间：提交、worker 开始/完成、pipe 接收、
   控制 poll、实际使用；区分 worker 源期限错误与交付后过期。

4. 改善近端真实双侧支持与局部边界拟合，量化延拓误差；随后再根据候选拒绝
