runs ported from `origin/main` (`docs/experiments/2026-10-14/evidence/car15/

## Reading the steering comparison

RMSE 0.17-0.28 (normalized steering, range [-1, 1]) between the MPC's shadow
candidate and the PID's logged action is a reasonable level of disagreement
for two different controllers (MPC's QP feedback law vs the PID's gain-based
one) fed the same real, noisy ordered_xy road -- not a sign either is wrong.
Using `mpc.vehicle_params_source: course_simulation` instead of the fitted
car .27 record roughly doubled this RMSE (0.41-0.45) by making the MPC's
drive request incomparable to the real car's (the course model needs far
less drive for 0.2 m/s than the car's measured ~0.29 deadband); that is a
replay-configuration pitfall, not a port finding, and is fixed in the tool.

## Reading "adapted ref vs logged trajectory"

This number is a replay-fidelity check, not a tracking-error metric -- see
the tool's own NOTE and docstring. On these three runs it is dominated by two
things that are NOT adapter bugs:
- most steps are `near_field_unobserved`/`near_field_requires_both_
  boundaries`, where `planning.allow_forward_only` accepts a forward-only
  (truncated-near-end) centerline; the PID's logged Path can legitimately
  cover a different near-end range, inflating a nearest-point distance;
- `mpc.reference_dropout_tolerance_s` bridges brief road dropouts that the
  PID's logged Path does not (main's own documented "reference-handoff
  jump", SIMPLE_CENTERLINE_FOLLOW_CN.md).
Motion-transporting the logged points into the current tick's frame before
comparing (rather than comparing two different-time base_link snapshots
directly) changed this number by under 3%, so frame staleness is not the
explanation. Use `--json-out`'s per-step `road_status`/`mpc_branch` to look
at a specific `t` before treating a large number here as a regression.

## What this does and does not show

Shows: the ported ORDERED_CENTERLINE adapter and anti-jump path projector run
cleanly over three full ~20 s real right-angle-estimation-era car15 runs
(1180 control steps total), produce a finite, in-budget MPC candidate on
every tick Planning accepts (93.6%/91.2%/91.9% of ticks), and never crash or
emit a non-finite output. Does not show: that the MPC would have tracked
these roads as well as, better or worse than the PID -- that needs an actual
closed-loop run (shadow candidates are open-loop single-step evaluations
against the PID's own trajectory, not an independent rollout).
